# Install And Reset

## Install State Contract

- `InstallState` in `src-tauri/src/services/install/types.rs` is the frontend/backend contract for the install page. It includes selected paths, Steam launch-option support, game/mod state, compatibility state, action gates, resettable-data and BepInEx-folder status, and warnings. Warnings cross the boundary only as `InstallWarningCode` plus string parameters, never backend-authored display copy — see `InstallWarning`/`InstallWarningCode` in the same file and `install_warnings` in `src-tauri/src/services/install/mod.rs`.
- Reset returns typed `ResetBppDataResult` and `ResetBepinexResult` values, containing the refreshed state and removal outcome, in `src-tauri/src/services/install/types.rs`.
- `install_state_from_snapshot` in `src-tauri/src/services/install/mod.rs` derives game/mod/compat facts, resettable-data status, action gates, and warnings from one completed detection snapshot.
- The `get_install_state` command in `src-tauri/src/commands/install.rs` calls `build_install_state` in `src-tauri/src/services/install/mod.rs`, which resolves through `detect_for_install` in `src-tauri/src/services/detect/mod.rs`. That function waits on `InstallerContextState::get_or_initialize` in `src-tauri/src/services/startup.rs` — the same process-wide `OnceLock` that the `setup()` closure in `src-tauri/src/lib.rs` warms eagerly in a background task before the frontend can call in — so the first successful frontend response is a real native detection rather than an all-false bootstrap seed.
- The Install workflow owns a route-scoped discriminated snapshot, `InstallPageSnapshot` in `src/features/install/installWorkflow.ts`, with initial-loading, blocking-failure, and ready states. `DefaultInstallWorkflow.loadState` preserves the last valid `InstallState` on a refresh failure and ignores stale completions via its request-id counter. `DefaultInstallWorkflow.deriveSnapshot`, together with `deriveInstallPrimaryAction`, derives one primary action plus complete action availability from that same snapshot. `PrimaryInstallActionButton` in `src/features/install/PrimaryInstallActionButton.tsx` consumes that snapshot rather than recomputing mode in the route.

## Install And Uninstall

- `install` in `src-tauri/src/services/install/operation.rs` is one operation: `classify_payload` classifies the payload as missing, changed, or current; it gathers launch-mode facts; `execute_and_refresh` executes private planned effects through `ProductionInstallEffects`, stops on the first effect error, and otherwise returns only a freshly detected `InstallState`.
- `plan_install` in `src-tauri/src/services/install/plan.rs`: a current payload with an already-satisfied launch mode produces no effects, but `execute_and_refresh` in `operation.rs` still runs the final refresh; missing or changed payloads install BepInEx, while launch-mode-only repair leaves a current payload intact.
- Marker-before-Steam-clear, close-Steam-only-on-mode-switch, prefix-marker-last, and payload-before-bundle-mutation remain private planner invariants encoded in `plan_install`'s ordering and pinned by `test_ordering_constraints_hold_for_every_input_combination`, both in `src-tauri/src/services/install/plan.rs`.
- Prefix/trampoline ordering, fresh/missing/changed/current payload states, current-install no-op, launch-mode-only repair, first-error truncation, and refresh-after-success are tested through the `Recorder` effect recorder in the `tests` module of `src-tauri/src/services/install/operation.rs`; no command or service caller observes the planned effect vector, since `InstallEffect` stays private to the install module.
- Every command in `src-tauri/src/commands/install.rs` returns `SemanticProblem`. The service boundary classifies detection (`install_detection_problem`), and classifies generic actions, game-running resets, and partial reset failures into stable codes and parameters (`install_action_problem`), both in `src-tauri/src/services/install/mod.rs`; the frontend maps those codes to bilingual recovery copy via `installProblemMessageKey`/`presentInstallProblem` and keeps diagnostics separate in `src/features/install/installProblems.ts`.
- Install pre-clean removes only BPP-owned files the incoming payload no longer ships, in `prepare_install_target` and `remove_stale_bpp_files` in `src-tauri/src/services/bepinex/payload.rs`; `extract_zip` in `src-tauri/src/services/bepinex/zip_archive.rs` skips byte-identical existing files and overwrites the rest. Third-party files are never pre-deleted, but a colliding path with different content is still overwritten by extraction.
- Ownership is defined by `BPP_PRIVATE_RELATIVE_PATHS` and `BPP_BUNDLED_DEPENDENCY_RELATIVE_PATHS` in `src-tauri/src/services/bepinex/payload.rs`; `test_ownership_lists_match_release_contract` in the same file pins those lists to a release-contract filename set. `runPrebuildCheck` in `scripts/prebuild-check.mjs` validates each platform zip through `validatePayloadZip` in `scripts/payload-zip.mjs`, which requires the staged `SourceForBuild` inputs (`assertRequiredStagingInputs`), enforces exact zip/staging agreement (`validateZipEntrySet`), and rejects stray OS artifacts (`.DS_Store` and the like) in both the staged tree (`listPayloadFiles`) and the zip entries (`normalizedEntryName`).
- Uninstall is gated on `has_third_party_plugins` and `has_third_party_patchers` in `src-tauri/src/services/bepinex/payload.rs`, checked by `uninstall_bpp` in `src-tauri/src/services/bepinex/mod.rs`: when another mod's plugin (in `BepInEx/plugins`) or patcher (any file under `BepInEx/patchers`) is present, only private BPP files are removed and shared dependencies, trampoline, launch options, and BepInEx bootstrap stay; when BPP is the last mod, the full payload, trampoline, launch-mode marker, Steam launch options, and BepInEx bootstrap are removed — the bootstrap through `remove_bootstrap_files` in `src-tauri/src/services/bepinex/payload.rs` — which lets `is_bepinex_installed` in `src-tauri/src/services/detect/game.rs` return false.
- Uninstall never touches the `BazaarPlusPlusV5/` data directory; only the explicit Reset flow removes it via `cleanup_bpp_data_directory` in `src-tauri/src/services/bepinex/payload.rs`.

## Reset Local Data

- The Install workflow opens target-bearing install, delete/reset, and uninstall confirmations that fix the game path at request time — `requestInstall`, `requestResetData`, `requestResetBepinex`, and `requestUninstall` in `src/features/install/installWorkflow.ts`. Install may still edit the pending compatibility choice while confirming, via `setPendingCompatOptIn`; `DefaultInstallWorkflow.executeConfirmed` then locks path and compatibility at execution. React owns only ephemeral acknowledgement checkboxes (install and destructive deletes) and modal presentation, in the `Install` page component (`src/pages/Install.tsx`) and the `ResetDataConfirmModal`, `ResetBepinexConfirmModal`, and `UninstallConfirmModal` components (`src/features/install/`). Once native work starts, Escape, backdrop, close, and secondary dismissal are blocked — each modal's `activeDismissalPolicy` becomes `{ kind: 'blocked' }` while busy — because none of these commands is cancellable.
- The delete-local-data tile is disabled from workflow availability when reset is not allowed, and the UI distinguishes "no local data" title/detail from the destructive action copy, in `InstallActionsPanel` in `src/features/install/InstallActionsPanel.tsx`.
- Reset data treats an already-empty state as a no-op notice, otherwise calls `resetBppData`, replaces state from the typed result, and chooses removed versus nothing-to-delete notice codes from `removed_data` — the `'reset-data'` case in `DefaultInstallWorkflow.executeConfirmed`, `src/features/install/installWorkflow.ts`. Confirmation closes only on success and retains the exact target and problem on failure, in `ConfirmedOperationController.run`, `src/features/shared/confirmedOperation.ts`; `DefaultInstallWorkflow.confirm` orchestrates that run and allows retry-or-safe-close from the `failed` phase, and `executeConfirmed`'s catch clause reconciles state against the fixed target via `DefaultInstallWorkflow.reconcile` before the failure is published.
- `reset_bpp_data` in `src-tauri/src/services/bepinex/mod.rs` enters `StreamRuntime::exclusive_maintenance` in `src-tauri/src/stream/runtime.rs`, which stops and awaits the stream task and keeps lifecycle operations excluded throughout blocking deletion.
- Reset refuses to run while The Bazaar is detected as running, records whether the data directory existed before cleanup, and returns stable error-code prefixes for blocked or partial-failure cases, in `reset_bpp_data_blocking` and the `RESET_BPP_DATA_ERR_GAME_RUNNING`/`RESET_BPP_DATA_ERR_PARTIAL_FAILURE` constants, `src-tauri/src/services/bepinex/mod.rs`.
- Raw reset sentinels remain private to the Rust service boundary; the frontend consumes only semantic problem parameters, maps them to localized messages via `installProblemFromError`/`installProblemMessageKey`, and extracts partial-failure paths via `installFailurePaths`, all in `src/features/install/installProblems.ts`.
