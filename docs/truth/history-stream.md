# History And Stream

## History Data Access

- The History facade resolves the current Selected game installation, privately derives database/game/video storage paths, and owns list, detail, reveal, delete, and cleanup operations through the `History` struct in `src-tauri/src/services/history.rs`; it does not borrow Stream runtime state.
- List/detail resolution emits `history_unavailable` from `History::from_resolved_game_path_for_page`. An unsupported mod database schema emits `history_database_unsupported_schema` with `found` and `expected` parameters, and other SQLite/query failures emit `history_read_failed` with a stable operation parameter and optional diagnostic; both come from the `history_read_problem_with` helper in `src-tauri/src/services/history.rs`. A read failure that coincides with a still-running game process emits `history_read_blocked_by_game` instead, because that is the one cause the user can act on — `history_read_problem_with` consults the injected `History.is_game_running` callback, which production construction in `History::from_resolved_game_path` sets to `game_process::is_bazaar_running_best_effort` in `src-tauri/src/services/game_process.rs`, whose Windows-only probe means the code cannot occur elsewhere. Screenshot reveal, video reveal, and video delete failures emit `history_action_failed` with their target operation through the shared `history_action_problem` helper, also in `src-tauri/src/services/history.rs`. Their shared serialized contract is the `SemanticProblem` struct and `SemanticProblemCode` enum in `src-tauri/src/problem.rs`, and it crosses the Tauri command boundary through the `#[tauri::command]` functions (e.g. `list_history_runs`, `execute_storage_cleanup`) in `src-tauri/src/commands/history.rs`.
- The `get_history_run_detail` Tauri command in `src-tauri/src/commands/history.rs` returns a successful nullable detail, so an absent run is distinct from an unavailable installation or failed read; `History::run_detail_for_page` in `src-tauri/src/services/history.rs` carries the same nullable-detail contract.
- Tauri History commands (`list_history_runs` through `execute_storage_cleanup` in `src-tauri/src/commands/history.rs`) pass only domain inputs such as ids, limits, cleanup scope, and preset to the facade; command signatures contain no database, game, video-directory, cutoff, or cleanup-plan values. Cleanup preview/execute return `SemanticProblem` from `History::preview_cleanup_for_page` and `History::execute_cleanup_for_page`, with unavailable selection classified separately and native failures carrying stable `preview_storage_cleanup` or `execute_storage_cleanup` operation parameters via the shared `history_action_problem` helper — all in `src-tauri/src/services/history.rs`.
- Every connection, read or write, opens the BazaarPlusPlus SQLite database with `SQLITE_OPEN_READ_WRITE` and a two-second busy timeout, in `open_probed` (called from `open_connection` and `open_write_connection`) in `src-tauri/src/history/queries.rs`. Read paths do not open read-only: a read-only connection can neither create a missing `-shm` nor recover a dirty WAL, which is the state the game leaves behind when it exits uncleanly. Write access is not thereby required of reads — SQLite opens a write-protected file read-only by itself.
- Because opening is lazy, the `PRAGMA user_version` query inside `open_probed` is both the probe that proves the connection can reach the database and the schema guard enforced by `validate_supported_schema`, both in `src-tauri/src/history/queries.rs`. A failed probe is retried twice at 50 ms and 150 ms (`OPEN_RETRY_BACKOFF`, consumed by `open_with_retry`, same file) when the SQLite code is busy, locked, or I/O, and never for a schema mismatch. Diagnostics carry the SQLite extended code via `describe_error`, also in `src-tauri/src/history/queries.rs`.
- `open_write_connection` additionally rejects — inside `open_probed` — a database SQLite has silently downgraded to read-only, so an unwritable file fails at open rather than partway through a cleanup transaction, in `src-tauri/src/history/queries.rs`.
- History summary counts runs, completed runs, wins, latest run timestamp, and completed combat replay videos in `load_summary` in `src-tauri/src/history/queries.rs`.
- The run list orders by end/last-seen/start timestamp descending, with run id as tie-breaker, in `list_run_rows` in `src-tauri/src/history/queries.rs`.
- History maps the legacy `Hero8` and canonical `TheDragons` values to the display name `The Dragons` for both run heroes and battle opponents, while preserving absent opponent heroes and other hero names, via `canonical_hero_id`/`hero_display_name` in `src-tauri/src/history/hero.rs` and `build_run_shared_fields`/`map_battle_row` in `src-tauri/src/history/mapper.rs`.
- Primary screenshots prefer explicit primary rows and fall back to latest `end_of_run_auto` screenshots in `primary_screenshot_ids` and `primary_screenshot` in `src-tauri/src/history/screenshots.rs`.

## History UI

- History independently starts list loading and status-only preview discovery via `useHistoryPage`'s `refreshHistory` and `refreshPreview` callbacks in `src/features/history/useHistoryPage.ts`; it never ensures or starts a Stream session. Stopped/failed Stream status becomes a non-blocking preview problem through `loadHistoryPreviewCapability` in `src/features/history/historyPreview.ts`, which switches the row fallback label computed in `RunRow` in `src/pages/History.tsx`; image load failures fall back inside the row via `RunPreview`'s `onError` handler in the same file.
- The History page state union makes initial loading, blocking failure, ready-empty, and ready-content exclusive, while refreshing and refresh failure retain successful data, through the `PageState` type in `src/features/shared/pageState.ts`, `HistoryPageState`/`reduceHistoryPageState` in `src/features/history/historyPageState.ts`, and the default-exported `History` component in `src/pages/History.tsx`.
- The History page renders Runs, Videos, and Win Rate summary cards via the `SummaryCard` component in `src/pages/History.tsx`.
- The ready-empty branch of the `History` component explains why run data is missing and offers a busy-gated Refresh action plus a secondary link back to Install, in `src/pages/History.tsx`.
- A `history_read_blocked_by_game` banner (`HistoryProblemBanner` in `src/pages/History.tsx`) offers an End Game Process action that terminates every `TheBazaar.exe` and reloads on any outcome, since an already-exited process leaves the same stale error on screen as one just ended. The action is `useHistoryPage`'s `endLeftoverGameProcess` callback in `src/features/history/useHistoryPage.ts`, which calls the `end_game_process` Tauri command in `src-tauri/src/commands/game.rs`, backed by `terminate_processes` in `src-tauri/src/services/process_snapshot.rs`.
- History rows link to `/history/:run_id` details and show a lazy-loaded, async-decoded preview image beside the run's hero, locale-formatted start date, result, and wins/days/rank/rating metrics, via `RunRow` and `RunPreview` in `src/pages/History.tsx` and `formatDateTime` in `src/features/history/format.ts`.
- Run detail makes initial loading, not-found, blocking failure, and ready content exclusive; refresh failure retains the last successful detail and stale completions are ignored, through `RunDetailPageState`/`reduceRunDetailPageState` in `src/features/history/runDetailPageState.ts` and the default-exported `RunDetail` component in `src/pages/RunDetail.tsx`. Empty battle lists render `EmptyState` with a refresh action in that same `RunDetail` component.
- Detail refresh, screenshot reveal, video reveal, and video deletion share one visible single-flight gate, driven by `RunDetailActionState` in `src/features/history/runDetailPageState.ts` and `useRunDetailPage`'s `runAction`/`load` in `src/features/history/useRunDetailPage.ts`; action failures stay scoped to the screenshot or affected battle (`actionProblemFor`) and clear when that target retries. The screenshot reveal control and its failure banner sit in `RunDetail` in `src/pages/RunDetail.tsx`; the video reveal/delete controls and their failure banner sit in `BattleRow` in the same file. Video deletion additionally runs through the framework-neutral `useConfirmedOperation` controller in `src/features/shared/confirmedOperation.ts`: the battle/video target (`{ kind: 'delete-video', battleId, videoId }`) stays visible across confirming, running, and failed phases; the confirmation dialog blocks dismissal while running; a failed delete retains a localizable semantic problem for retry or safe close; and the dialog closes only after `useRunDetailPage`'s `deleteVideo` dispatches the server's returned detail as a `data-replaced` event, which `replaceRunDetailData` in `src/features/history/runDetailPageState.ts` folds into the page's ready data before the confirmed-operation outcome resolves to success. The dialog itself is composed in `RunDetail` in `src/pages/RunDetail.tsx`.
- Run detail formats dates, replay durations, and replay sizes through shared locale-aware helpers — `formatDateTime` and `formatDuration`/`formatBytes` in `src/features/history/format.ts` — with replay metadata rendered beside each video action in `BattleRow` in `src/pages/RunDetail.tsx`.
- The History page renders the storage cleanup card (`StorageCleanupCard` in `src/features/history/StorageCleanupCard.tsx`) after the summary cards only in a successful ready state, inside the default-exported `History` component in `src/pages/History.tsx`; the card offers separate end-of-run screenshot and run-data rows, then confirms the exact scope, preset, counts, and consequence. Execute failure keeps that target and localized semantic problem in place for retry or safe close; success alone closes and refreshes History, via `useStorageCleanup` in `src/features/history/useStorageCleanup.ts`.

## Storage Cleanup

- Tauri exposes only `preview_storage_cleanup(scope, preset)` and `execute_storage_cleanup(scope, preset)` in `src-tauri/src/commands/history.rs`. Their Specta-generated success results are Serde scope-tagged unions — `StorageCleanupPreview` and `StorageCleanupExecution` — for `screenshots` and `run_data` in `src-tauri/src/services/history.rs`; failures use the shared semantic problem contract.
- `History::preview_cleanup` and `History::execute_cleanup` in `src-tauri/src/services/history.rs` derive the same preset cutoff for preview and execute before dispatching on scope, so a preview cannot promise a different set than the execute that follows it.
- The cleanup presets are the wire strings `all`, `older_than_7_days`, and `before_this_month` (`StorageCleanupPreset` in `src-tauri/src/history/cleanup.rs`); `CleanupCutoff::for_preset` in that same file computes non-`all` cutoffs from local time and stores UTC strings for SQL comparisons. A non-`all` preset never collapses to `None` (the wire meaning of `all`): a spring-forward DST gap at local month-start falls back to local noon.
- A completed non-PTR Ranked run is upload-protected only while it has neither a pending/uploaded `bundle_outbox` row nor a `terminal_failure` `bundle_seal_jobs` row — the `PROTECTED_RUN_PREDICATE` constant in `src-tauri/src/history/cleanup.rs`. Game mode and build channel comparisons are case-insensitive, and the same predicate drives run planning, skipped counts, screenshot protection, and both conditional execution deletes.
- Screenshot cleanup plans (`plan_screenshot_cleanup`) and executes (`execute_screenshot_cleanup_plan`) against `end_of_run_auto` rows, excludes a requested primary screenshot belonging to an upload-protected run (`eligible_screenshots`), counts each planned exclusion in `skipped_pending_uploads` (`pending_upload_count`), compares captured timestamps with `datetime()`, protects files still referenced by surviving rows, and sweeps only orphan dated-folder files — all in `src-tauri/src/history/cleanup.rs`. Execution conditionally rechecks protection before deleting each row (`delete_screenshot_if_unprotected`, same file), finishes all row-deletion transactions before unlinking, and excludes any plan-approved PNG path still named by a conditional-delete miss.
- The orphan sweep (`scan_orphan_screenshot_files` in `src-tauri/src/history/cleanup.rs`) skips any folder whose local date is at or after `min(cutoff_date, today_local_date)`, so today's local-date folder is always protected — even under preset `all`, where there is no cutoff — because the mod writes a screenshot's PNG (through an atomic `<name>.png.<guid>.tmp` rename) before it inserts the matching `run_screenshots` row, and an in-flight, not-yet-rowed file would otherwise be swept. `today_local_date` is derived from the same `chrono::Local::now()` that builds the cutoff in `History::preview_cleanup`/`History::execute_cleanup` in `src-tauri/src/services/history.rs`, then threaded into `scan_orphan_screenshot_files` (a capture straddling local midnight into yesterday's folder is a known, unclosed sub-second window left open by design rather than injecting a clock for an mtime grace check).
- Run-data cleanup plans only non-active runs outside the upload-protection predicate and protects screenshot/video files still referenced by kept rows, via `plan_run_data_cleanup` and `remaining_video_relative_paths_after_run_cleanup`/`remaining_screenshot_relative_paths_after_run_cleanup` in `src-tauri/src/history/cleanup.rs`.
- Run-data execution (`execute_run_data_cleanup_plan` in `src-tauri/src/history/cleanup.rs`) opens the FK-enabled cleanup connection and validates the four required cascade relationships (`validate_run_cleanup_cascade_fks`, same file) before any destructive side effect. For each planned run it first conditionally deletes `runs` inside a write transaction; only a successful guarded delete is followed by deletion of the planned non-cascading video and screenshot rows in that transaction. All row-deletion transactions finish before the unified unlink phase, where screenshot and video paths still named by guarded-delete misses are excluded. Cleanup file resolution refuses drive-relative escapes in `resolve_cleanup_file_path` in `src-tauri/src/history/files.rs`.
- `BundleOutbox/` and the `bundle_outbox` table belong to the mod. Cleanup neither deletes nor estimates their files or rows; the outbox deliberately has no `runs` foreign key. The FK-enabled cleanup connection (`open_cleanup_connection` in `src-tauri/src/history/queries.rs`) instead validates and uses cascades for `battles→runs`, `run_events→runs`, `battle_snapshots→battles`, and `bundle_seal_jobs→runs`, checked by `validate_run_cleanup_cascade_fks`/`has_on_delete_cascade_fk` in `src-tauri/src/history/cleanup.rs`.

## Stream Service

- The stream service binds to `127.0.0.1:17654` via the `HOST` and `PREFERRED_PORT` constants in `src-tauri/src/stream/server.rs`.
- `StreamRuntime` is the single lifecycle owner, in `src-tauri/src/stream/runtime.rs`. Its async lifecycle mutex serializes ensure, restart, stop, window changes, and exclusive maintenance; task handles and captured installation paths remain private to `StreamRuntimeInner`, in the same file.
- `StreamRuntime::ensure` and `StreamRuntime::restart` resolve one Selected game installation snapshot (via `resolve_installation`) while holding the lifecycle gate; window changes (`StreamRuntime::set_window_with`, calling `stream_window_for_offset`) reuse the captured record path instead of re-resolving a possibly changed selection — all in `src-tauri/src/stream/runtime.rs`.
- The production server adapter (`ProductionServer::start` in `src-tauri/src/stream/server.rs`) constructs the overlay repository and settings store, reports database/window status (`stream_db_status`/`stream_window_status`, same file), and serves the router with graceful shutdown; `StreamRuntime::stop_locked` in `src-tauri/src/stream/runtime.rs` sends shutdown and awaits the task before publishing idle state.
- Startup and window-close both use the runtime rather than composing server mutations directly: the `run()` setup closure calls `StreamRuntime::ensure` after building the tray, and the `on_window_event` close handler checks `StreamRuntime::snapshot` before hiding to tray, both in `src-tauri/src/lib.rs`. The stream Tauri commands (`ensure_stream_session`, `restart_stream_session`, `set_stream_window`) in `src-tauri/src/commands/stream.rs`, and the tray's `stop_stream_service` menu handler and `quit_app` function in `src-tauri/src/tray.rs`, all call through `StreamRuntime` the same way.
- Stream commands return `SemanticProblem`: service, display-window, and crop-setting failures keep stable capability and operation codes via `stream_service_problem`, `stream_window_problem`, and `stream_crop_problem` in `src-tauri/src/commands/stream.rs`, while native details remain optional diagnostics on the shared `SemanticProblem` struct in `src-tauri/src/problem.rs`.

## Stream UI Capabilities

- The Stream snapshot (`StreamPageSnapshot` in `src/features/stream/streamWorkflow.ts`) keeps service, polling freshness, display window, crop settings, and clipboard/opener actions as independent capability states with their own phase, operation, problem, and action gates, assembled by `DefaultStreamWorkflow.deriveSnapshot` in the same file.
- Service and crop initialization run independently — `DefaultStreamWorkflow.start` and `loadInitialCrop` in `src/features/stream/streamWorkflow.ts`; crop loading or failure does not block service/window controls, and crop plus one-off operations use separate single-flight gates (`runCropAction` and `runOneOff`, same file).
- Three consecutive status-poll failures (`POLL_FAILURE_THRESHOLD`, checked inside `DefaultStreamWorkflow.poll`) preserve the last value but mark it stale, disable actions that require an authoritative running service, and expose a manual refresh; a successful poll restores freshness. Both live in `src/features/stream/streamWorkflow.ts`, with the derived gating computed in `deriveSnapshot`.
- Workflow state stores semantic problems and notices — the `StreamProblem` type in `src/features/stream/streamProblems.ts` — rather than localized copy. Translation is a pure presentation step (`presentStreamProblem`/`presentStreamNotice` in that same file; `presentStreamSnapshot` in `src/features/stream/streamPresentation.ts`), and `useStreamPage` in `src/features/stream/useStreamPage.ts` creates the workflow once via `useMemo`, independently of locale, so language switches do not dispose, restart, or re-ensure the session.

## HTTP Surface

- The local HTTP router (`router` in `src-tauri/src/stream/http.rs`) exposes `/overlay`, `/settings`, stream record APIs, crop-config APIs, record images, and static overlay/settings assets.
- Stream records expose a canonical `hero_id` separately from the display `title`; `to_overlay_record` in `src-tauri/src/stream/records/mapper.rs` normalizes the legacy `Hero8` and canonical `TheDragons` database values (via `canonical_hero_id`/`hero_display_name` in `src-tauri/src/history/hero.rs`) to `hero_id: "TheDragons"` and `title: "The Dragons"`, while preserving other trimmed hero ids. The overlay chooses badge styling and assets from `hero_id` in `getHeroBadgeStyle`, with a direct `Hero8` fallback alias, in `src-tauri/resources/stream/overlay.js`.
- CORS is narrowed to Tauri origins and the local Vite dev origins `http://localhost:14207` and `http://127.0.0.1:14207` in `is_allowed_cors_origin` in `src-tauri/src/stream/http.rs`.
- `/settings` is served from the stream service's own origin, so it cannot read the app's stored locale. It carries its own zh/en dictionary (`MESSAGES`) and resolves the locale from a `?lang` query parameter before falling back to the browser language, via `resolveLocale` in `src-tauri/resources/stream/settings.js`; the app appends the current locale when opening the page, via `DefaultStreamWorkflow.openSettings` and the `withLocaleParam` helper in `src/features/stream/streamWorkflow.ts`. Request failures carry the raw response body, so the page logs it and shows localized status copy instead, in `reportFailure` in `src-tauri/resources/stream/settings.js`.
